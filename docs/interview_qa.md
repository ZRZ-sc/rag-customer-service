# 面试问答手册 —— 企业级智能客服 RAG 系统

> 用法：先看每题「30 秒版」（口述结论），再按需展开「要点与数字」；最后看「追问预案」。
> 所有数字均来自仓库内报告：`docs/eval_report.md`、`docs/loadtest_report.md`、`docs/gap_audit.md`、
> `docs/environment_notes.md`，可现场翻给人看。
> 环境基线：i7-12650H（10C/16T）/ 15.7GB 内存 / **无 GPU** / 单进程 uvicorn / 中间件跑在 WSL2 Docker 里。

---

## 开场：30 秒项目自述

> 这是一个电商智能客服 RAG 系统，用户问「我的订单到哪了」走 PostgreSQL 精确查询，问「退货运费谁出」走
> 混合检索 + 重排 + DeepSeek 生成。核心做了四件事：**意图路由**（政策优先→正则单号→关键词+LLM few-shot，
> 评测集意图准确率 100%）、**四级缓存 + 快速路径**（缓存复用 550-890ms，命中型流量压到 350 RPS，超需求 75%）、
> **多轮指代消解**（"那什么时候能到？"能关联到上文的订单号，并带跨用户泄漏护栏）、
> **可观测与降级**（Prometheus 20+ 指标、Grafana 15 面板、8 条告警；LLM/Milvus/Redis/PG 四条降级链 + LLM 熔断）。
> 79 条/91 轮次评测集上意图和答案都是 100%，500 并发 0 个 5xx；延迟目标 P99<500ms 因本机无 GPU 未达标，
> 这一点我不回避，后面可以详细说。

# A. RAG 检索（4 题）

## Q1. 为什么用「BM25 + 向量」混合检索，而不是只用向量？

**30 秒版**：向量擅长语义、BM25 擅长**精确字面**匹配（订单号、型号、"七天无理由"这类专有词）。
纯向量在电商 FAQ 上会把「可以指定快递公司吗」和「支持哪些快递公司」拉得很近但答案完全相反；
纯 BM25 又扛不住"退的钱啥时候能回我账户"这种口语同义改写。两者用 RRF 融合，互补。

**要点与数字**
- 向量侧：Milvus HNSW / COSINE，`M=16`、`efConstruction=200`、检索 `ef=128`；嵌入 bge-small-zh-v1.5（512 维，中文，本地 CPU）
- 关键词侧：`rank-bm25` 进程内索引，中文用 **bigram + 整词** 分词（`_tokenize`），避免引入 jieba/ES
- 融合：**RRF（k=60）**，无参数、不需要两路分数量纲对齐
- 评测集里有 6 条同义改写用例（"退的钱啥时候能回我账户"→ 退款到账），答案正确率 100%

**追问预案**
- *为什么不用加权求和？* → 两路分数分布不同（BM25 无上界、余弦在 0-1），归一化要调参且随语料漂移；RRF 只用排名，稳健。
- *为什么不上 ES？* → 42 条 FAQ 用进程内 BM25 足够且少一个中间件；语料上万条时再换 ES（方案书里也提到倒排索引），
  代码里 `HybridRetriever` 已经把两路检索封装成接口，替换成本低。

## Q2. 为什么要 Rerank？Cross-Encoder 和双编码器差在哪？

**30 秒版**：召回阶段向量/BM25 是"query 和 doc 分别编码再算相似度"，快但粗；重排用 Cross-Encoder 把
(query, doc) 拼起来过一遍模型，能看细粒度交互，精度明显更高。代价是**不能预计算、只能对少量候选逐个打分**，
所以我把它放在候选已经收敛之后。

**要点与数字**
- 模型：bge-reranker-base + **int8 动态量化**（~700MB）。文档原方案是 bge-reranker-v2-m3，但本机 16GB 内存
  加载 fp32 的 2.27GB 权重直接把 `torch_cpu` 搞崩，换成同族 base 后 CPU 上还快 2-3 倍
- 送重排的候选：完整路径 `RERANK_MAX_CANDIDATES=12`、快速路径 Top-5（文档写 50→5，我按 CPU 现实下调，
  配置项可一行改回）
- 打分：`sigmoid(logits)` 当置信度 → **Top-1 分数就是响应里的 `confidence`**，<0.5 触发兜底 + 转人工
- 分批推理 `batch_size=32`，避免大 batch 打满内存

**追问预案**
- *候选从 50 降到 12 会不会掉召回？* → 语料只有 42 条，Top-12 基本覆盖全部相关项；评测答案准确率 100%。
  语料变大后应把候选调回 50 并上 GPU。
- *为什么用 sigmoid 而不是 softmax？* → Cross-Encoder 单条打分是二分类 logit，sigmoid 给的是"这条相关"的绝对概率，
  softmax 会把一批候选归一化成相对值，跨请求不可比，也就没法当阈值用了。

## Q3. HyDE 和 Multi-Query 有什么用？你怎么实现的？

**30 秒版**：Multi-Query 把一个问题扩成多个角度提高召回；HyDE 先让模型编一段"假设性标准答案"，
再用它去做向量检索——因为用户口语和知识库书面语的向量空间距离较远，假设答案更接近知识库的表述。
我的实现特点是把这两件事**合并成一次 LLM 调用**，冷启动省约 1s。

**要点与数字**
- 一次调用同时产出 `{"queries": [...], "hyde": "..."}`，`MULTI_QUERY_COUNT=3`（文档 3-5 个）
- 多个查询**并行**检索（`asyncio.gather`），再对全部结果做全局 RRF 融合
- 结果缓存 24h（`query_transform:{sha1(问题)}`），键用"改写后的问题"，所以上下文相关的问题不会串
- 只在**完整路径**触发；高置信的快速路径直接跳过这步（这就是省 1s 的原因）

**追问预案**
- *这两步不是文档里分开的吗？* → 文档流程图标了两步，但都是"一次 LLM 生成 + 改善检索"，合并成一次调用
  语义不变、少一次网络往返；这是我在压测里发现"冷启动 2 次 LLM 调用"是延迟主因后做的优化。
- *HyDE 幻觉怎么办？* → 假设答案只用于检索，**不进 prompt**，最终生成仍严格基于检索到的 FAQ 上下文，所以幻觉不会外泄到答案里。

## Q4. 你说的「快速路径」是什么？阈值怎么定的？

**30 秒版**：基础混合检索（不调 LLM）之后先看置信度：如果 Top-1 向量余弦 ≥0.80 **且** 与 Top-2 有 ≥0.05 的分差，
说明这条 FAQ 已经足够明确，就直接对它做重排再生成，跳过昂贵的 Multi-Query/HyDE。
压测时这个快速路径命中率 **49%**，冷启动首答从 2.2-2.9s 降到 **0.76-1.35s**。

**要点与数字**
- 只看**向量原始分**（RRF 分是排名分，不能当阈值），所以融合时特意把 `vector_score` 保留下来
- 双条件是为了防"两条 FAQ 分数咬得很近但都不确定"的情况（分差太小说明语义模糊，宁可走完整路径）
- 命中率 49%，即完整路径的 LLM 扩展开销省掉近一半

**追问预案**
- *0.80/0.05 怎么来的？* → 在评测集上扫的：低于 0.80 会放进同义改写的误命中，高于 0.85 命中率掉到 30% 以下
  （收益不划算）。这两个都是配置项（`FAST_PATH_MIN_SCORE` / `FAST_PATH_MIN_MARGIN`）。
- *快速路径会不会牺牲准确率？* → 评测集答案准确率仍 100%；因为重排仍在，只是候选范围小了。

# B. 四级缓存（3 题）

## Q5. 四级缓存分别是哪四级？为什么这么设计？

**30 秒版**：按"越靠前越省事"排：L1 答案缓存（1h）直接返回；L2 上下文改写（24h）省一次改写 LLM；
L3 查询扩展 Multi-Query/HyDE（24h）省一次扩展 LLM；L4 重排结果（24h）省 CPU 重排。
分别对应 RAG 链路里四个昂贵的环节，任意一级命中都能砍掉一段耗时。压测口径 L1 命中率 **63.2%**。

**要点与数字**
| 级别 | Key | TTL | 省掉什么 |
|---|---|---|---|
| L1 | `rag:answer:{归一化问题}` | 1h | 整条 RAG（命中 2-7ms） |
| L2 | `query_rewrite:{问题}:{上下文指纹}` | 24h | 改写 LLM（~0.6s） |
| L3 | `query_transform:{sha1(问题)}` | 24h | 扩展 LLM（~1.0s） |
| L4 | `rerank:{问题}:{候选 faq_id 列表}` | 24h | CPU 重排（~0.85s） |
- 精确查询**不缓存长时**：订单状态实时性要求高，只给 30s 短缓存（文档要求 30-60s）
- 请求进来先做 **L1 早期探测**：独立问题（不需改写）直接查答案缓存，命中就返回，连会话历史和改写都不做
- 缓存写入前先过**护栏**（见 Q12）：`_GUARD_VERSION="g2"` 混进缓存键，护栏规则升级时旧缓存自动失效

**追问预案**
- *为什么不直接缓存 embedding？* → 嵌入是本地的、单次 query 编码只要几毫秒，真正贵的是 LLM 与重排，
  缓存粒度放在"阶段产物"收益更大。

## Q6. 缓存一致性怎么保证？

**30 秒版**：两条线——**TTL 兜底** + **写时主动失效**。知识库更新（`ingest_kb.py`）在写库后主动清除
答案/扩展/重排三级缓存；改写缓存不依赖知识库，但它的键里混了护栏版本号，规则变了键就变了。
另外低置信度答案和 LLM 失败话术**一律不写缓存**，避免把坏结果固化 1 小时。

**要点与数字**
- `ingest_kb.py` 幂等更新（`ON CONFLICT (question) DO UPDATE`，version+1），完成后清 `answer=.. transform=.. rerank=..`
- Milvus 侧先按 `faq_id` 删旧向量再插入，避免同一文档残留多条向量（这也是"重复插入"缺陷的修复）
- 缓存操作全部打点 `cache_operation_total{name,result}`，Grafana 上能看每一级的命中/写入

**追问预案**
- *缓存击穿/穿透/雪崩呢？* → 诚实说：**没做单飞（singleflight）防击穿、没有空值缓存防穿透、TTL 也没加随机抖动**。
  当前流量形态（热点集中、问题有限）没暴露这个问题，但这是我知道的下一步（压测报告"尚可优化"一节也记了）。
  被追问时给出方案：热点 key 加互斥锁/单飞、空结果短 TTL 缓存、TTL 加 ±10% 抖动。

## Q7. 精确查询为什么不缓存？和知识类的缓存策略有什么不同？

**30 秒版**：订单状态是**实时数据**，用户刚付款就看"已发货"是事故。所以精确查询只给 30s 短缓存，
而知识类（退货政策这种）几天不变，给 1h 甚至 24h 都没问题。**缓存时长应该由数据的变化频率决定，而不是由技术便利决定。**

**要点与数字**
- 精确查询缓存键 `precise:{单号}:{user_id}`——**带用户维度**，防止 A 用户命中 B 用户的订单结果
- 精确查询 `confidence=1.0`（文档规定），知识类取重排 Top-1 分
- 30s 短缓存在压测里对 DB 压力贡献明显：画像②纯精确查询 312 RPS 时 PostgreSQL 连接池（20）都没打满

# C. 多轮指代消解（3 题）

## Q8. 多轮对话怎么做的？为什么改写要放在意图识别之前？

**30 秒版**：会话存 Redis（`session:{id}`，最近 10 轮，30 分钟过期）。关键设计是**改写必须发生在意图识别之前**：
用户说"那什么时候能到？"，原始问题里没有订单号，正则和 LLM 都会判成知识类，结果答非所问。
先结合历史把它改写成"订单 ORD20240100001 什么时候能到？"，后面的正则、检索、缓存键才都正确。

**要点与数字**
- 改写不是每题都做：`needs_rewrite()` 判断"含代词/指示词（那/它/这个/刚才）、极简追问、无实体但像在问订单状态"才触发；
  首轮、自带订单号、独立完整问题直接跳过（零额外开销）——这是控制成本的关键
- 改写结果缓存 24h，键包含**上下文指纹**（会话实体 + 上一轮问题）
- 会话历史 10 轮 / 30 分钟 TTL，与文档流程4 一致
- 评测集里有 12 轮多轮用例（状态追问 + 政策追问），全绿

**追问预案**
- *为什么不用向量检索历史？* → 会话只有 10 轮且强依赖指代关系，规则判断 + LLM 改写的确定性更高、成本更低。

## Q9. 改写用的 LLM 挂了怎么办？

**30 秒版**：三级兜底。① LLM 改写失败 → 用**会话实体记忆**确定性地把订单号补进问题（`entity_memory` 方法，
不依赖 LLM）；② 记忆也没有 → 直接用原问题继续走，不阻塞主流程；③ 整个 LLM 层不可用 → 熔断（见 Q13），
改写直接短路。**降级的目标是"服务质量下降"，不是"接口报错"。**

**要点与数字**
- 实体记忆存在 `session:{id}:entities`，记录本会话最近提到的订单号/物流单号（最多各 5 个，与对话同 TTL）
- 实测：把 `DEEPSEEK_BASE_URL` 指向不可达地址，接口仍返回 200 兜底话术，不会 500（见 Q13）
- 还有一道**政策护栏**：原始问题带"运费/换货/多久到账"这类政策词时，即使 LLM 注入了订单号也要剥掉，
  否则会被正则误判成订单查询（这个坑我在评测里踩过：多轮政策追问被路由到数据库）

## Q10. 改写缓存为什么要带「上下文指纹」？

**30 秒版**：同样一句"那什么时候能到？"，在不同会话里指代的订单完全不同。如果缓存键只用问题文本，
B 用户会拿到 A 用户的改写结果——这是**缓存键设计导致的数据越权**。所以键 = 问题 + 会话实体 + 上一轮问题摘要。

**要点与数字**
- `rewrite_cache_key(question, fingerprint)`；压测显示 L2 命中率只有 7.8%，**这正是设计意图**：
  跨会话天然不该命中，宁可多花一次 LLM 也不能串用户
- 同样的思路用在 L4：`rerank:{问题}:{候选 faq_id 列表}`，候选集变了就不能复用旧打分

# D. 跨用户实体泄漏（2 题）★ 最能体现排查能力的一题

## Q11. 压测里那 1172 个 403 是怎么回事？

**30 秒版**：这是压测帮我抓到的**真实越权缺陷**，比容量数字有价值。压测脚本为省资源让不同用户共用一批
`session_id`；而"可以指定快递公司吗？"这种以"吗？"结尾的 FAQ 被追问判定误判，LLM 改写时把**同一 session 里
别的用户**的订单号注入了问题 → 正则命中订单号 → 路由到订单查询 → 归属校验失败 403。
**根因是：会话级上下文没有做用户维度隔离。**

**要点与数字**
- 现象：首轮压测 1,172 个 403（"无权限查询该订单"），失败率 0.08%
- 链路：`needs_rewrite` 判定过宽（把"吗？"结尾的正常 FAQ 当追问）→ LLM 从历史里借了实体 → 正则快路径命中单号 → 越权
- 定位方法：从 403 的 request_id 反查日志里的 `intent/entities/rewritten`，发现改写结果里夹带了不属于该用户的订单号

## Q12. 你怎么修的？怎么保证不再发生？

**30 秒版**：三处收口 + 10 个回归测试。① 用**严格的状态意图判定**替代宽泛信号词；② 收紧追问判定（极简追问限 ≤8 字）
并新增**实体注入护栏**（原问题不是状态类问题时，改写结果不得夹带订单号）；③ **实体记忆与写入用户绑定**，
别人读返回空。修完压测 403 归零，评测集 9 条越权用例全绿。

**要点与数字**
- `intent.py::has_status_intent()`：只认"到哪/进度/签收/什么时候到/状态"这类强信号，且**政策词优先否决**
- `query_rewrite.py::_apply_guards()`：两道护栏（policy_guard / entity_guard），在**缓存读取和写入两侧都执行**
  （只做写入侧的话，24h 旧缓存会把护栏绕过去——这个我踩过）
- `conversation.py`：实体记忆带 `user_id`，读取时校验 owner，不一致返回空（记 warning 日志）
- 回归测试 +10：护栏剥离、缓存旁路、跨用户隔离、政策问法优先于实体
- 类比总结：**"会话"不是安全边界，"用户"才是** —— 共享 session_id（同一浏览器多账号、多端登录）在真实客服系统里很常见

**追问预案**
- *为什么不让 LLM 改写时只用当前用户的历史？* → 更彻底的方案是历史也按用户隔离（Redis key 加 user 维度）；
  当前是"记忆层隔离 + 护栏"，成本更低。若做多端登录，会把 `session:{user}:{session}` 作为键。

# E. LLM 熔断与降级（2 题）

## Q13. LLM 挂了你的系统会怎样？

**30 秒版**：四层处理。① 生成失败 → 返回固定话术「抱歉，系统繁忙，请稍后再试」+ **自动转人工工单**，
HTTP 仍是 200、`source=fallback`，而且**不写缓存**；② 连续失败触发**熔断**，冷却期内所有 LLM 调用毫秒级短路；
③ 意图/改写/扩展这些前置 LLM 调用各有兜底（默认知识类 / 实体记忆 / 原问题检索）；④ 其它依赖也有降级：
Milvus 挂 → PG `ILIKE` 全文检索，Redis 挂 → 跳过缓存直连 PG，PG 挂 → 500 + 告警。

**要点与数字**
- 修复前：生成异常直接冒泡成 **HTTP 500**，与需求文档流程6 的"固定话术"要求不符（审计时发现的真实缺口）
- 修复后实测（把 base_url 指向不可达地址）：

  | 请求 | 耗时 | 行为 |
  |---|---|---|
  | 第 1 次（熔断前） | 61.0s | 真实失败一次 → 立刻打开熔断 → 后续调用短路 |
  | 第 2 次 | **0.6s** | 全程短路，直接返回兜底话术 + 工单号 |
  | 第 3 次 | **0.2s** | 同上 |

- 熔断参数：`LLM_CIRCUIT_THRESHOLD=3`，但**超时/连接类异常一次即打开**（这类失败每次要耗满 timeout，代价最高）；
  `LLM_CIRCUIT_COOLDOWN=30s` 后放行一次探测，成功即恢复

## Q14. 为什么用熔断，而不是加长超时/多试几次？

**30 秒版**：因为**重试救不了宕机，只会把线程和用户时间一起烧掉**。实测 DeepSeek 不可达时，OpenAI SDK 自己会
重试+指数退避，一次失败调用占 12~55 秒；如果并发请求都堆在重试上，接口整体不可用——这正是 N8 要避免的。
熔断把"每次都慢 60 秒"变成"只慢一次，之后 0.2 秒给兜底话术 + 转人工"。

**要点与数字**
- 阈值定 3（+硬失败立即打开）的理由：单次抖动不该熔断，两次以上连续失败基本可判定上游故障
- 冷却 30s 的理由：太短会持续打不可用的上游，太长会让恢复变慢；30s 后放行"探测请求"，成功即关闭
- 配套可观测：`llm_failure_total{stage}`（含 `:circuit_open` 短路计数）、`/ready` 的 `llm` 组件新增
  `circuit_open` 状态、2 条 Prometheus 告警（熔断打开 / 失败偏高）
- **为什么必须单独告警**：熔断期间接口全是 200，错误率告警根本不会响 —— 这是"降级成功但业务已受损"的典型盲区

**追问预案**
- *熔断会不会误伤？* → 冷却期后立刻放一次探测，恢复很快；且熔断只影响 LLM 相关能力，订单查询、缓存命中、
  静态页面全部照常。
- *多实例下熔断状态怎么共享？* → 当前是**进程内**熔断（单进程部署够用）。多副本时应把状态放 Redis（共享计数 +
  打开时间），或者交给服务网格/API 网关的熔断器——这点我在 `docs/production_plan.md` 里写了。

# F. 压测与瓶颈定位（3 题）

## Q15. 你怎么定位瓶颈的？说说方法。

**30 秒版**：三步。① **分档加压**（50/100/200/300/500 并发阶梯）看吞吐-延迟曲线拐点；② **换流量画像**做对照实验——
我设计了三套画像（缓存命中型 / 纯精确查询 / 全冷启动 RAG），**两条后端完全不同的画像都卡在同一吞吐**，
就直接排除了数据库嫌疑，指向 Web 层的每请求固定开销；③ **同机采样** CPU/内存/依赖指标，用 Prometheus 看
缓存命中率、快速路径占比、各环节耗时。

**要点与数字**
| 画像 | 吞吐上限 | 瓶颈判定依据 |
|---|---|---|
| 缓存命中型 | **350 RPS** | 50 并发就接近上限，并发翻 6 倍吞吐不涨、延迟线性涨 → 队列堆积（Web 层固定开销 ~3ms/请求） |
| 纯精确查询 | 312 RPS | 与画像①几乎一样，PostgreSQL 20 连接池远未打满 → **瓶颈不在 DB** |
| 全冷启动 RAG | **5 RPS** | 延迟 2-3.7s 且**不随并发增长** → 单请求被外部依赖（LLM + CPU 重排）锁死 |
| 500 并发 | 331 RPS，0 个 5xx | P99 从 3.6s 劣化到 8.2s，仍无错误 → 缺背压 |

- Web 层 ~3ms/请求的构成：中间件 + 鉴权 + Redis 会话读取 + `dialogue_logs` 插入 + JSON 日志 + 序列化
- 优化手段按收益排序：多进程（注意每个 worker 要独立加载模型）、问答日志异步/批量写、Nginx 多副本

## Q16. 为什么冷启动 RAG 只有 5 RPS？怎么优化？

**30 秒版**：因为一次冷启动要串行等三件外部的事：改写 LLM + 扩展 LLM + 生成 LLM（DeepSeek 远程往返 0.4-2.4s 波动），
中间还夹一次 CPU 重排（峰值打满 CPU）。**吞吐不是被并发限制，是被单请求的串行依赖限制的**——这也是我后来做
四级缓存和快速路径的直接动机：把冷启动路径变成"命中路径"。

**要点与数字**
- 优化已落地：快速路径（命中率 49%）跳过扩展 LLM，冷启动从 2.2-2.9s → 0.76-1.35s；缓存复用 550-890ms
- 还能做的：① 本地 vLLM 推理替代远程 API（消除网络往返，文档 3.2 原方案）；② GPU 重排（文档目标 150ms，
  当前 CPU ~850ms）；③ `RERANK_MAX_CANDIDATES` 12→8；④ 流式返回首字降低体感延迟

## Q17. 500 并发 0 个 5xx，但你为什么说这是问题？

**30 秒版**：因为**没报错不代表没问题**。P99 从 3.6s 涨到 8.2s、吞吐却停在 331 RPS，说明请求全在队列里排队——
这是"软失败"：用户等了 8 秒，而系统没有任何保护动作。正确做法是**加背压**：超出容量就快速失败（429），
而不是无限排队把所有人的延迟一起拖垮。

**要点与数字**
- 压测时为了测真实容量**故意关了应用层限流**（300 次/分/身份会先触发 429）
- 已有的限流能力：Redis 令牌桶（Lua 原子扣减，fail-open）、Nginx 层 `limit_req` 20r/s + burst 40；
  容器化实测 120 个并发请求 → 83 个 200 + **37 个 429**，符合"超额卸载而非雪崩"的设计
- 计划：`RATE_LIMIT_GLOBAL_PER_MINUTE` 全局桶 + uvicorn `--limit-concurrency` 双重背压

# G. 环境事故处理（2 题）

## Q18. 讲一个你排查过的疑难问题。

**30 秒版**：讲"C 盘写满导致 WSL 根文件系统只读"这次。**最迷惑的点是：所有读接口都是绿的，只有写失败**——
L1 缓存命中、Milvus 检索、RAG 生成全部正常，但 PostgreSQL 落库报 `could not open file "base/16384/2601":
Read-only file system`，Redis 报 AOF MISCONF，Docker 构建卡在提交镜像层。
根因是 Windows C 盘剩余空间归零，而 WSL 的虚拟磁盘在 C 盘，ext4 触发保护把根文件系统 remount 成只读。

**要点与数字**
- 定位链：Docker 报 `read-only file system` → 进 WSL `mount | grep ' / '` 看到 `emergency_ro` →
  `touch` 测试确认只读 → `Get-Volume` 发现 C 盘 0GB 可用 → 查到 Ubuntu 的 `ext4.vhdx` 在 `C:\Users\...\wsl\`
- 处置：先退出抢着拉起发行版的 Docker Desktop 与保活窗口（否则 `wsl --manage --move` 报
  `WSL_E_DISTRO_NOT_STOPPED`）→ `wsl --shutdown` → **`wsl --manage Ubuntu --move D:\WSL\Ubuntu`（9 秒完成）**
  → C 盘 0GB → **10.68GB 可用**，容器随 `restart: unless-stopped` 自动恢复 healthy
- 收尾：把 `autoMemoryReclaim=gradual` + `sparseVhd=true` 写进 `.wslconfig`（**必须放 `[experimental]` 段**，
  放 `[wsl2]` 下 WSL 会报无法识别），避免内存压力让 Windows 页面文件（当时已膨胀到 12.36GB）再次撑满 C 盘
- 沉淀：写成 `docs/environment_notes.md`，含复现命令与预防清单

## Q19. 从这个事故里你学到了什么？

**30 秒版**：两点。① **监控要看"写入是否成功"，不能只看探针绿不绿**——读路径全绿、写路径全红的情况下，
`/ready` 依然返回 ok，健康检查完全失灵；所以我建议加"最近 5 分钟 dialogue_logs 是否有新增"这类**业务级健康度**告警。
② **降级逻辑的价值在故障时才体现**：正因为对话日志、自动转人工、限流都是 fail-open/失败不影响主流程，
磁盘只读期间接口仍在正常回答，用户侧几乎无感，问题只停留在日志和后台统计里。

**要点与数字**
- 事故期间的真实表现：问答返回 200，但日志里持续出现 `dialogue log write failed` / `auto handoff failed` 告警
- 另一个教训：**长任务（Docker 构建）失败时先怀疑环境再怀疑代码**——当时 Dockerfile 的 apt 与 pip 全部执行成功，
  只有"提交镜像层"失败，这个分界线本身就指向文件系统而不是依赖安装

# H. 未达标项与诚信边界（3 题）★ 面试官最爱问

## Q20. N2（P99<500ms）没达标，你怎么解释？

**30 秒版**：我直接承认没达标，并说清边界：这个指标在需求文档里是**按 GPU + vLLM 推理的预算拆解的**
（重排 <150ms 靠 GPU、LLM <200ms 靠 vLLM），而我的验证环境是**无 GPU 的 16GB 笔记本、单进程**，
CPU 重排一次就 ~850ms、DeepSeek 远程往返 0.4-2.4s，物理上不可能进 500ms。
我在这个环境里能做的是把"命中路径"做到极致，并把冷启动的组成讲清楚。

**要点与数字**
- 分场景实测：L1 缓存命中 **2-7ms**（已远优于目标）；缓存复用 **550-890ms**；冷启动快速路径 **0.76-1.35s**；
  完整路径 2.2-2.9s
- 压测口径（50 并发缓存画像）：P50 54ms / P95 640ms / P99 970ms——**P50 达标、P99 未达标**
- 达标路径（已写进 `docs/production_plan.md` 与压测报告）：GPU 重排、本地 vLLM、SSE 流式返回首字、
  多副本水平扩展
- 态度：**不把"缓存命中 2ms"包装成"P99 达标"**；指标口径和场景必须一起说，否则就是自欺欺人

## Q21. N3（可用性 99.9%）和 N6（链路追踪）呢？

**30 秒版**：N3 我**没有**给出 99.9% 的实测结论，因为那需要长时间稳定运行数据或多副本故障演练，
单机 demo 环境下算出来的数字没有意义。我的处理是把它拆成"架构能力"来交付：健康探针、自动重启、
四条依赖降级链、熔断、限流卸载，并把多副本/K8s 方案写进生产方案文档。
N6 里 Prometheus + Grafana + 结构化日志都落地了，**唯独 LangSmith 没实测**——代码开关接好了，
但这个网络环境访问不了并且没有 API Key，我用 `request_id` + `trace_id` 贯穿日志、配合 Prometheus 面板替代，
能力上等价（能按请求串联各阶段耗时），只是没有现成的可视化 trace 界面。

**要点与数字**
- 已落地：`/health` + `/ready`（含依赖与熔断状态）、容器 healthcheck、`restart: unless-stopped`、
  4 条降级链、20+ 指标、15 面板、**8 条告警规则**
- 日志：loguru JSON，字段含 `request_id / trace_id / user_id / session_id / service / duration_ms / status`，
  且手机号/邮箱/身份证/地址/`sk-*`/Bearer/JWT 全部脱敏，禁记明文 token
- 补齐 LangSmith 的成本：**填一个 `LANGSMITH_API_KEY` 并打开开关**即可（代码已就绪）
