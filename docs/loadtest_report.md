# RAG 智能客服 —— 高并发压测报告（N1 / N5）

> 工具：Locust 2.46.6 ｜ 脚本：`loadtest/locustfile.py` ｜ 结果原始数据：`loadtest/results/*.csv`

## 一、测试环境与方法

| 项目 | 配置 |
|------|------|
| 被测服务 | `uvicorn app.main:app --port 8001`（**单进程**，`PRELOAD_MODELS=false`，`RATE_LIMIT_ENABLED=false`） |
| 硬件 | i7-12650H（10 核 16 线程）／物理内存 15.7GB（压测启动时空闲 ~4.9GB） |
| 中间件 | PostgreSQL / Redis / Milvus 运行于 WSL2 内 Docker（约占 2GB） |
| LLM | DeepSeek API（远程，网络往返 0.4~2.4s 波动） |
| 本地模型 | bge-small-zh-v1.5 + bge-reranker-base(int8)，首次 RAG 请求懒加载（~1.6GB） |
| 负载生成器 | Locust 与**被测服务同机**（共享 CPU/内存）→ 客户端指标是服务端能力的**下界** |
| 压测前状态 | 42/42 高频 FAQ 答案缓存已预热（L1 命中） |

**为什么关闭限流**：应用层限流默认 300 次/分钟/身份，会先于容量瓶颈触发 429，无法测出真实上限。
限流本身的行为已在第一阶段验收中单独验证（突发 9 次 → 5 次放行 + 4 次 429）。

**三套负载画像**（不同画像的瓶颈完全不同）：

| 画像 | 流量构成 | 目的 |
|------|---------|------|
| ① cache | 70% 缓存命中的 FAQ + 30% 订单/物流查询 | 测**吞吐上限**（真实客服的主要流量形态） |
| ② precise | 100% 订单/物流查询（归属用户正确配置） | 测**DB/连接池**承载 |
| ③ rag | 100% 冷启动知识问答（问题带唯一后缀，必然不命中任何缓存） | 测 **LLM + CPU 重排**饱和点 |

## 三、瓶颈定位（均有数据支撑）

### 瓶颈1：单进程事件循环的「每请求固定开销」——决定 ~350 RPS 天花板 ★最关键

- **证据**：两条后端完全不同的画像（Redis+PG vs 纯 PG）**都卡在 ~310-350 RPS**；
  失败率 0（排除依赖故障）；并发从 50 升到 300，吞吐不变而延迟线性上升 → 典型队列堆积
- **构成**：中间件 + 鉴权 + 会话读取(Redis) + `dialogue_logs` 插入(PG) + JSON 结构化日志 + 序列化 ≈ 3ms/请求
- **调优手段（按收益排序）**：
  1. **多进程**：`uvicorn --workers N` —— 但注意每个 worker 需独立加载模型（见瓶颈3），需配合独立推理服务
  2. **关闭/异步化问答日志写入**：`DIALOGUE_LOG_ENABLED=false` 或改为后台批量写入（省一次 PG 往返）
  3. **前置 Nginx 多副本**（需求文档 3.7 已规划）：N 个副本可线性提升吞吐
  4. 降低日志冗余（`AUTH_DEBUG_LOG` 已在生产配置中关闭）

### 瓶颈2：冷启动 RAG 仅 ~5 RPS

- **证据**：10 并发下延迟 2~3.7s 且**不随并发增长**（说明单请求耗时由外部依赖决定，不是排队）；
  CPU 峰值 100%（重排参与饱和）；每次冷启动需 1 次改写 LLM + 1 次生成 LLM + 12 候选 CPU 重排
- **调优手段**：
  1. **提高快速路径命中率**（当前 49%）：下调 `FAST_PATH_MIN_SCORE` 0.80→0.75，减少 LLM 扩展
  2. **GPU 重排**（需求文档目标 150ms）或更小 Cross-Encoder
  3. **本地 vLLM 推理**替代远程 API（文档 3.2 节原方案），消除网络往返
  4. `RERANK_MAX_CANDIDATES` 12→8（完整路径重排 -30%）

### 瓶颈3：内存是硬约束，限制了水平扩容

- **证据**：压测中启动第二个带模型的实例直接崩溃 `OSError: 页面文件太小 (os error 1455)`；
  单实例模型常驻 1.6GB，Python 进程峰值 2.65GB
- **调优手段**：把**模型推理独立为单独服务**（如 Triton / 独立 FastAPI + GPU），Web 层多副本共享；
  或改用 API 化嵌入/重排（牺牲延迟换内存）

### 瓶颈4：高并发下缺少背压

- **证据**：500 并发时 P99 从 3.6s → 8.2s，但仍无 5xx —— 请求全部在队列里等待
- **调优手段**：开启应用层 429 限流（`RATE_LIMIT_GLOBAL_PER_MINUTE`）或 uvicorn `--limit-concurrency`，
  在过载时快速失败而非无限排队；配合 Nginx `limit_req`

### 瓶颈5：L2/L3/L4 缓存命中率偏低（7.8% / 2.8% / 6.3%）

- **原因**：L2 的键包含"上下文指纹（会话实体+上一轮问题）"，跨会话天然不命中；
  L3/L4 在冷启动画像中按设计必然 miss（唯一问题后缀）
- **调优手段**：L2 指纹简化为仅会话实体；对相似问句做归一化（如去标点/同义归一）以提高 L1 覆盖率

## 四、达标判定

| 需求 | 目标 | 实测 | 判定 |
|------|------|------|------|
| **N1 吞吐** | QPS > 200 | 缓存型流量 **350 RPS**（精确查询 312 RPS） | ✅ **达标**（超 75%） |
| **N5 并发** | ≥500 并发连接 | 500 并发全部被服务，0 个 5xx/连接错误 | ✅ **达标**（P99 劣化至 8.2s） |
| **N2 延迟** | P99 < 500ms | 50 并发缓存命中 P95 640ms / P99 970ms；高并发 P99 数秒 | ⚠️ **单机不达标**（需 GPU 重排 + 多副本） |
| 错误率 | — | 0.08%（全部为测试数据越权 403，无服务故障） | ✅ |
| 冷启动 RAG | — | 5 RPS（LLM/CPU 上限） | 记录为容量参考 |

## 五、压测中发现并修复的真实缺陷 ★

压测暴露了一个**跨用户上下文泄漏**问题，价值高于容量数字本身：

1. **现象**：首轮压测出现 **1,172 个 403**（"无权限查询该订单"）
2. **定位**：`CacheHitUser` 用同一批 `session_id`（`lt-cache-{n%50}`）服务不同用户；
   短的 FAQ 问题（如"可以指定快递公司吗？"，以"吗？"结尾）被 `needs_rewrite` 判为追问 →
   LLM 把**同一 session 中其他用户**的订单号注入改写结果 → 正则命中订单号 → 路由为订单查询 → 越权 403
3. **修复（三处 + 10 个回归测试）**：
   - `intent.py`：新增 `has_status_intent()`（"状态意图"严格判定），替代宽泛信号
   - `query_rewrite.py`：① 收紧追问判定（极简追问限 ≤8 字）② 新增**实体注入护栏**（原问题非状态类时，改写结果不得夹带实体）
   - `conversation.py`：**实体记忆与写入用户绑定**，他人读取返回空（跨用户隔离）
4. **验证**：修复后同样的 500 并发压测，403 从 1,172 → 40（遗留会话）→ 清理会话后 0

## 六、复现步骤

```powershell
# 1) 启动压测专用实例（无模型预加载、无限流；端口与生产实例隔离）
$env:PRELOAD_MODELS="false"; $env:RATE_LIMIT_ENABLED="false"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8001

# 2) 预热缓存（保证 ① 画像测的是稳态吞吐而非冷启动）
.\.venv\Scripts\python.exe -m scripts.warmup_cache --base http://127.0.0.1:8001 --limit 20

# 3) 依次压三套画像（LT_STAGES = 用户数:持续秒）
$env:LT_BASE="http://127.0.0.1:8001"
$env:LT_PROFILE="cache";   $env:LT_STAGES="50:30,100:30,200:45,300:45"
.\.venv\Scripts\python.exe -m locust -f loadtest\locustfile.py --headless --csv loadtest\results\cache --html loadtest\results\cache.html
# 同理跑 precise（100:30,200:45,300:45）与 rag（3:30,5:30,10:45）

# 4) 汇总结果（含分档位吞吐/延迟/失败与资源峰值）
.\.venv\Scripts\python.exe -m loadtest.summarize --prefix loadtest/results/cache --resource loadtest/results/resource_all.csv
```

**注意事项**
- 压测实例必须与生产实例分端口，避免污染线上指标
- 生成器与被测服务同机时，客户端指标偏悲观；如需精确容量，应把 Locust 部署到另一台机器
- 冷启动画像会产生真实 LLM 费用（每请求 2 次调用），建议控制并发与时长
- `LT_PROFILE=mixed` 时会额外启用 401 鉴权路径（实测该路径可承载 ~130 RPS）

## 七、结论与下一步

1. **当前单机配置可稳定支撑 ~350 RPS**（N1 达标），500 并发连接可被接受（N5 达标）
2. **要达成文档的 P99<500ms**，必须补齐两项基础设施：**GPU 重排**与**本地 vLLM 推理**，
   并将模型推理与 Web 服务解耦以支持多副本
3. **优先级建议**：① 开启限流做背压（防雪崩）→ ② 多副本 + Nginx → ③ 推理服务独立化 → ④ GPU 重排
