# 生产环境扩展方案（架构演进路径与预估收益）

> 基线数据全部来自本机实测（见 `docs/loadtest_report.md`），非理论估算。
> 基线环境：单进程 uvicorn + 本机 CPU 模型（bge-small-zh-v1.5 嵌入 / bge-reranker-base int8 重排）
> + 远程 DeepSeek API，10 核 16 线程 CPU、16GB 内存、无 GPU。

## 一、当前架构与实测基线

```
                     ┌──────────────┐
  客户端 ──────────► │  单进程 uvicorn │ ──► Redis / PostgreSQL / Milvus（容器）
                     │  模型常驻 1.6GB │ ──► DeepSeek API（远程）
                     └──────────────┘
```

| 指标 | 实测值 |
|------|--------|
| 缓存命中型吞吐上限 | **350 RPS**（N1 目标 >200 ✅） |
| 纯精确查询吞吐 | 312 RPS（PostgreSQL 未打满，0 失败） |
| 冷启动 RAG 吞吐 | **5 RPS**（LLM 等待 + CPU 重排） |
| 500 并发 | 331 RPS，0 个 5xx，但 P99 由 3.6s 劣化到 **8.2s** |
| 延迟（服务端） | P50 0.49s / P95 1.36s / P99 1.5~4.2s；缓存命中 2~7ms |
| 资源 | CPU 峰值 100%，Python 进程峰值 2.65GB，空闲内存最低 2.19GB |

**已定位的四个瓶颈**（详见压测报告第三节）：
1. 单进程每请求固定开销 ≈3ms → 350 RPS 天花板
2. 冷启动 RAG 受 LLM 往返 + CPU 重排双重限制
3. 内存硬约束：模型副本 1.6GB/实例，第二份即触发 `os error 1455`
4. 高并发缺背压：排队而非快速失败

## 二、演进路径（按收益/成本排序）

### 阶段 A：入口层背压与多副本（成本最低，1-2 天）

**改动**：
- 启用 Nginx 入口限流（`nginx/nginx.conf` 已内置 `limit_req`，超限返回 429，与应用错误码一致）
- 应用层限流打开并配置全局桶：`RATE_LIMIT_ENABLED=true`、`RATE_LIMIT_GLOBAL_PER_MINUTE`
- `docker compose up -d --scale app=3` 水平扩展（前提：模型推理已外置，见阶段 B；否则单机内存只能跑 1 个副本）

**预期收益**：
- P99 在 500 并发下由 8.2s 回落到 **1s 级**（队列不再无限增长，超载请求快速 429）
- 配合多副本，吞吐随副本数近似线性：3 副本 ≈ **900-1000 RPS**（受限于共享的 Redis/PG）
- 可用性：副本滚动更新 + 健康检查（`/ready`）支撑 99.9% 目标

**风险**：限流阈值需按业务压测标定，过紧会误伤正常用户（建议先观察 `rate_limited_total` 指标）。

### 阶段 B：模型推理独立化（收益最大，3-5 天）★推荐优先

**问题**：嵌入与重排模型与 Web 进程同生命周期 → 每副本 +1.6GB 内存、模型加载阻塞首请求、CPU 争抢。

**改动**：把模型推理拆成独立服务（任选其一）
| 方案 | 说明 | 适配度 |
|------|------|--------|
| **TEI**（HuggingFace Text Embeddings Inference） | 官方推理服务，支持 bge 系列，自带动态批处理 | 嵌入首选 |
| **Triton Inference Server** | 通用、支持 ONNX/TensorRT、并发模型实例 | 重排首选（含 GPU） |
| 自建 FastAPI 推理服务 | 复用现有 `embeddings.py` / `reranker.py`，暴露 `/embed`、`/rerank` | 改动最小，1 天可落地 |
| 云 API（SiliconFlow / DashScope bge） | 零运维，按量付费 | 快速验证，长期成本高 |

Web 层通过 `EMBEDDING_SERVICE_URL` / `RERANK_SERVICE_URL` 调用；本地模型代码保留为降级路径。

**预期收益**：
- Web 副本内存从 1.6GB 降到 **~250MB** → 同机可跑 **6-10 个副本**
- 消除模型加载阻塞，冷启动首请求不再有 60s 抖动
- 推理侧可独立扩容，配合动态批处理（batch 32+）吞吐提升 **3-5 倍**

### 阶段 C：GPU 重排（延迟收益最直接，1-2 天）

**问题**：CPU 交叉编码器重排 12 个候选约 0.85s，是冷启动 RAG 的第二大耗时。

**改动**：重排服务部署到 GPU（Triton + bge-reranker，或 vLLM 兼容的 rerank 端点），
`RERANK_MAX_CANDIDATES` 可回调至文档设计的 50（CPU 上不得不降到 12）。

**预期收益**：
- 重排耗时 0.85s → **0.15s 以内**（需求文档 3.3 节的目标值）
- 冷启动 RAG P95 由 3.2s 降到 **~1.2s**（剩余为 LLM 往返）
- 检索质量回升：候选数 12 → 50，召回更充分

### 阶段 D：本地 LLM 推理替代远程 API（延迟与成本双收益，3-5 天）

**问题**：远程 DeepSeek API 单次往返 0.4~2.4s 且波动大（实测冷启动 LLM 占 2.4s 中的绝大部分）。

**改动**：按需求文档 3.2 节原方案部署 **vLLM**（PagedAttention，吞吐提升 5-10 倍），
或将高频问句的生成结果更多地交给缓存（当前 L1 命中率 63%，见阶段 E）。

**预期收益**：
- LLM 生成 0.6-2.4s → **0.2-0.4s**（本地 GPU）
- 冷启动 RAG P95 有望进入 **<1s**，配合缓存使整体 P99 <500ms 接近达标
- 无外部调用费用；但需 GPU 投入与模型运维

### 阶段 E：缓存与命中率优化（纯软件，0.5 天）

**问题**：L2/L3/L4 命中率仅 7.8%/2.8%/6.3%（压测实测）。

**改动**：
- L2（改写缓存）键去掉"上一轮问题"指纹，只保留会话实体 → 命中率预计提升 2-3 倍
- 相似问句归一化（去标点、同义归一、问句模板化）提升 L1 覆盖率
- 上线前用 `scripts/warmup_cache.py` 预热 Top-N 高频问题（已支持启动自动预热）
- 缓存分层 TTL 调优：高频问题 TTL 延长、政策类问题 TTL 24h

**预期收益**：L1 命中率 63% → **80%+**，等效于把 20% 的请求从"秒级"搬到"毫秒级"。

### 阶段 F：可观测性闭环（已在阶段4完成，此处列出生产增强）

- Prometheus + Grafana 已就绪（15 面板 + 6 条告警）
- 生产建议补充：Alertmanager 接钉钉/企业微信、日志集中采集（Loki/ELK）、
  LangSmith 或自建链路追踪（当前因网络不可达未接入）

## 三、容量模型（按阶段组合估算）

| 配置 | 吞吐上限 | 冷启动 RAG P95 | 500 并发 P99 | 说明 |
|------|---------|---------------|-------------|------|
| **当前单机**（实测） | 350 RPS | 3.2s | 8.2s | 基线 |
| A：+限流+3 副本 | ~1000 RPS | 3.2s | ~1.0s | 需先做 B（内存约束） |
| A+B：+推理外置+6 副本 | **~2000 RPS** | 3.0s | ~0.8s | 副本线性扩展，推理侧动态批处理 |
| A+B+C：+GPU 重排 | ~2000 RPS | **~1.2s** | ~0.6s | 重排不再是瓶颈 |
| A+B+C+D：+本地 vLLM | ~2000 RPS | **<1s** | **~0.5s** | 接近 P99<500ms 目标 |
| 叠加 E（缓存优化） | 同上 | 同上 | 同上 | 等效降低 20% 的"重"请求占比 |

> 注：吞吐上限还受 Redis/PostgreSQL/Milvus 共享实例限制；上表假设中间件侧已按
> 读写分离/连接池扩容/独立部署做过相应调整。

## 四、落地步骤（推荐顺序）

```bash
# 1) 入口背压（当天可完成）
#    nginx.conf 已内置 limit_req；启用应用层全局桶
RATE_LIMIT_ENABLED=true
RATE_LIMIT_GLOBAL_PER_MINUTE=12000     # 按实测 350 RPS × 副本数 × 安全系数标定

# 2) 模型推理外置（先嵌入、后重排）
docker compose up -d embedding-service rerank-service
EMBEDDING_SERVICE_URL=http://embedding-service:8080
RERANK_SERVICE_URL=http://rerank-service:8081

# 3) 应用多副本 + Nginx 负载
docker compose up -d --scale app=3
#    nginx.conf 的 upstream 中列出 app-1/app-2/app-3（或用 Docker DNS 轮询）

# 4) GPU 重排 → 5) 本地 vLLM → 6) 缓存命中率优化
```

**每一项上线后都应复跑同一套压测**（`loadtest/locustfile.py` 三画像）核对收益，
并用 `scripts/eval_accuracy.py` 确认准确率未回退（基线：意图 100% / 答案 100%）。

## 五、风险与注意事项

| 风险 | 说明 | 缓解 |
|------|------|------|
| 限流误伤 | 阈值过紧会把正常用户挡在门外 | 先观察 `rate_limited_total`，灰度调整；按身份而非仅按 IP |
| 多副本下会话一致性 | 会话历史与实体记忆在 Redis（共享）✅；但内存态（BM25 语料）需每副本各自加载 | 启动时加载语料（已有），知识库更新后滚动重启或加管理接口触发重载 |
| 推理服务成为新单点 | 所有副本依赖同一个推理服务 | 推理服务多实例 + Nginx/gRPC 负载均衡 + 客户端重试与降级（保留本地模型兜底路径） |
| GPU 资源成本 | 重排与 LLM 都需要 GPU | 先上重排（收益/成本比最高），LLM 视流量增长再评估 |
| 缓存一致性 | 知识库更新后旧答案仍可能命中 | 已有 `ingest_kb` 主动清理三级缓存；多副本环境建议加版本号前缀 |
| 观测成本 | 15 面板 + 6 告警需有人响应 | 接入 Alertmanager 通知渠道，明确 on-call 轮值与处置 SOP |

## 六、结论

1. **当前单机配置已满足 N1（350 RPS > 200）与 N5（500 并发可用）**，可直接支撑中小规模业务
2. **要达成文档的 P99<500ms**，最短路径是：限流背压 → 模型推理外置 → GPU 重排 → 本地 vLLM
3. **投入产出比最高的第一步是"模型推理独立化"**：它同时解决内存约束、副本扩展与冷启动抖动三个问题
4. 全部优化均为**可增量上线**：每一步都能独立验证收益，且保留降级路径（本地模型 / 远程 API）
